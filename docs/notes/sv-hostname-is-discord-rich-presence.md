⚠ **CORRECTED 2026-08-06, same day it was written.** The first version of this note claimed
`sv_hostname` on the server is what every player's Discord shows, and that setting it was a free ad
surface. **That is WRONG.** The presence reads the **client's own** copy. Keeping the note because the
mechanism, the disproof and the colour table are all worth having - but the operational conclusion is
inverted: **there is no server-side lever on the Discord line.**

## What is actually true

Plutonium's Discord rich presence is generated by the **player's own**
`plutonium-bootstrapper-win32.exe` (it ships `bin\discord_game_sdk.dll` and carries
`plutonium::t5::rich_presence::startup` alongside t4/t6/iw5). It composes the card from
`cl_ingame`, `mapname`, `g_gametype`, `sv_hostname`, `sv_maxclients`, plus `"%s on %s"`,
`"Main menu"`, `"connect %s"` and the image key `pluto_t5%s`.

The catch: it reads those out of the **local dvar table of the machine it runs on**. `mapname` and
`g_gametype` are correct there because the client loaded the map. **`sv_hostname` and `sv_maxclients`
are not replicated into a client's dvar table**, so they stay at that client's registered defaults.

A live card, connected to the Gunfight VPS:

```
Plutonium T5: Multiplayer          <- the Discord APPLICATION name (not ours to change)
Gunfight on Hanoi                  <- "%s on %s", correct: the client knows these
2:06   BlackOpsPrivate (5 of 32)   <- sv_hostname + sv_maxclients, BOTH client-local
```

Three independent proofs that line is client-side:

1. **`(5 of 32)`** - the player count 5 was correct, but the server runs **`sv_maxclients 14`**.
   32 is the client's own default.
2. **The defaults differ by session type, and we see the CLIENT's.** `t5mp.exe` picks the default with
   a two-way select at VA `0x584BF1` (the only two refs to either string, 7 bytes apart):
   `Dvar_RegisterString("sv_hostname", <public/LSG session> ? "BlackOpsPublic" : "BlackOpsPrivate", 5, "")`.
   A live RCON read on the dedicated server reports **`default: "BlackOpsPublic"`**. The player's card
   said **`BlackOpsPrivate`**. If the presence read anything server-derived it could never produce the
   private string.
3. The presence code lives in the **client's** bootstrapper process, not on the box.

⚠ So a server owner **cannot** brand this line. Every player sees their own local `sv_hostname`, which
for anyone who has never hosted is the engine default. The only person who ever sees a real name there
is a **listen-server host**, who *is* the server.

## Second finding: sv_hostname is not runtime-settable

An RCON `set sv_hostname` appears to work and then **reverts at the next map load** - Plutonium
re-asserts the value it cached at server init. Proven by elimination on a live server that had not
restarted: in one session `set gf_scratch_probe` **stuck**, `set sv_motd` **stuck**, and
`set sv_hostname` **reverted within seconds** back to the boot-time string - while `dedicated.cfg` on
disk already held the new value (so a cfg re-exec could not be the source).

Treat it like `sv_wwwBaseURL`: **cfg-at-launch only, needs a restart**, not an RCON change.
Same for `sv_motd` taking effect - a server that booted without an `sv_motd` line renders a blank MOTD
for its whole life no matter what you set over RCON afterwards.

## Still worth knowing

- `sv_hostname` is **not** the server-browser name either - that is the Plutonium server-key label
  ([[plutonium-serverkey-sets-browser-name]]). Between that and this note, `sv_hostname` turns out to
  drive **almost nothing** player-visible: it is serverinfo hygiene, not a message surface.
- The surfaces that DO work are in [[plutonium-menu-ads-not-moddable]]: `sv_motd` (join/intel
  loadscreen), the server-key label, the in-game HUD/menu layer, and the join splash.
- `dedicated.cfg` is box-owned and **not shipped by `deploy.ps1`**; the tracked
  `server/dedicated.cfg.example` is documentation only.

## Ruled out while chasing this (do not re-derive)

Discord's game-detection database (all 23,888 `applications/detectable` entries fetched - nothing named
`BlackOpsPrivate`, and neither `plutonium-bootstrapper-win32.exe` nor `t5mp.exe` is listed); the window
title/class (`CoDBlackOps` / "Plutonium T5 Multiplayer (rNNNN)"); PE version info on every candidate
exe; the registry; and any named mutex/event/file-mapping. The string exists in exactly one place on
disk: `t5mp.exe`, as that dvar default.

⚠ **The RCON panel cannot show you a colour code.** `tools/rcon/server.js:171`'s `parseDvarValue` runs
`/\^[0-9a-zA-Z]/g`, so `^3` vanishes from `/api/dvars` output while `^<` survives (`<` is not
alphanumeric). Read the raw `POST /api/rcon` echo when you need the true value - this cost a wrong
conclusion once.

## The real T5 colour-code table (this part stands)

From `t5mp.exe` at `0x6C2CE8` (VA `0xAC3AE8`), 17 vec4 entries. The parser is the 19-byte function at
file offset `0x14BC70`, and there is **no digit check at all**:

```asm
mov   al, [esp+4]      ; the char after '^'
sub   al, 0x30         ; index = char - '0'
cmp   al, 0x11         ; 17 = table size
movzx eax, al
jb    use_it           ; 0..16 -> real entry
mov   eax, 7           ; else WHITE fallback
ret
```

Its one caller (`0xFC78D`, the only xref to the table) re-checks `cmp eax, 0x11` then `shl eax, 4` +
table base. So codes run past `^9` into ASCII punctuation, `^A`+ falls back to white, and a char below
`'0'` wraps unsigned onto white too. The bound of **17** is the tell that punctuation codes are real -
a digits-only parser would need 10.

`^0` black · `^1` red (1, .2, .2) · `^2` green · `^3` pale yellow · `^4` blue · `^5` cyan · `^6` pink ·
`^7` `^8` `^9` **all plain white** (forum lists claiming grey/brown are wrong for T5) · `^:` dark red ·
`^;` sea green · **`^<` ORANGE** (`0.97 0.58 0.11` = `#F7941C`) · `^=` steel blue · `^>` light grey ·
`^?` purple · `^@` brown.

These render wherever the **game** draws text: `sv_motd`, chat, the server-key label. They do **not**
survive into Discord - Plutonium strips `^0`-`^9`, `^:`, `^;` before publishing (regex
`\^\d|\^:|\^;`), so anything from `^<` up would publish **literally**. Moot for `sv_hostname` now that
the server cannot drive that line at all, but it still applies to any string Plutonium forwards.
